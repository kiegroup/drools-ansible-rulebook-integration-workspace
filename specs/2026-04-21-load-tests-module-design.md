# Design — `drools-ansible-rulebook-integration-load-tests` module

**Date:** 2026-04-21
**Branch:** `reorganize-load-test`
**Status:** Approved design; implementation planning next.

## 1. Context

The existing `drools-ansible-rulebook-integration-main` module has accumulated several responsibilities: a CLI entry point (`Main`), a memory-leak analyzer utility, unit tests (`PerfTest`, `SlownessTest`), ~30 JSON event-payload resources, and 7 load-test shell scripts with heavy duplication (PostgreSQL container setup, JVM invocation, stderr parsing, output formatting).

The load-test scripts and supporting infrastructure need a clean home. This spec introduces `drools-ansible-rulebook-integration-load-tests` as a greenfield sibling module that will gradually absorb load-testing responsibilities from `main`.

## 2. Goals

- A new Maven sub-module `drools-ansible-rulebook-integration-load-tests` that builds a fat jar, dependency on `drools-ansible-rulebook-integration-runtime` so HA (via PostgreSQL) works out of the box.
- Five load-test scripts covering three single-scope runs (`load_test_match.sh`, `load_test_unmatch.sh`, `load_test_retention_noHA_HA-PG.sh`) and two combined runs split by HA cost profile (`load_test_match_unmatch_noHA.sh`, `load_test_match_unmatch_noHA_HA-PG.sh`).
- Shared bash helpers in `lib/common.sh` so scripts stop reimplementing PG setup, JVM invocation, and stderr parsing.
- Small, single-responsibility Java classes that split the current `Main.java` into a CLI entry, per-mode runners, a measurement helper, a metric reporter, and an outcome checker.
- Deterministic, realistic 24KB event payloads (multi-field, non-repetitive) generated by a committed `PayloadGenerator` whose output JSON files are also committed.
- `MemoryLeakAnalyzer` ported into the new module and enhanced to understand the HA-PG suffix so the combined `load_test_match_unmatch_*.sh` scripts can emit one result file covering all modes.
- Every load test covers both noHA and HA-PG. If the run produces an unexpected match outcome (match scenario with zero matches; unmatch/retention scenario with one or more matches), the runner throws and the run fails loudly.

## 3. Non-goals (deferred follow-ups)

**Hard constraint: `drools-ansible-rulebook-integration-main` must not be modified by this task.** No file additions, deletions, renames, or edits under `drools-ansible-rulebook-integration-main/`. The only permitted change outside the new module is a single `<module>` line added to the root reactor `pom.xml`. The existing `main` module keeps its current scripts, resources, and `MemoryLeakAnalyzer` copy; duplication with the new module is accepted on purpose.

- Migrating `main`'s remaining load-test scripts (`load_test_90kb.sh`, `load_test_failover.sh`, `load_test_ha_compare.sh`, `load_test_temporal.sh`) — follow-up branch.
- Removing `MemoryLeakAnalyzer` / the load-test JSONs / the load-test scripts from `main` — follow-up after the new module is proven.
- H2 support (no bare `--ha` flag, no H2 file cleanup) — add when a migrated script needs it.
- `--failover-recovery` / `--ha-uuid` flags — add when `load_test_failover.sh` migrates over.
- 90KB payload variants — add when `load_test_90kb.sh` migrates over.
- CI wiring to run the combined `load_test_match_unmatch_*.sh` scripts automatically — operator-run for now.
- Per-HA-mode tuning of `MemoryLeakAnalyzer` thresholds — revisit after real runs show whether flat thresholds misfire.

## 5. Java-side contracts

### 5.1 `LoadTestMain`
CLI entry class.

```
Usage:
  java -jar drools-ansible-rulebook-integration-load-tests-jar-with-dependencies.jar
       <events-json> [--ha-db-params <json>]

Args:
  <events-json>         Resource name (classpath) or filesystem path,
                        e.g. "24kb_1k_events.json".
  --ha-db-params <json> JSON describing the HA DB (PostgreSQL). Presence
                        implies HA-PG mode.

Exit:
  0 on success; non-zero on failure (exception propagation).

Stderr (final line on success):
  "<events-json>[ (HA-PG)], <usedMemoryBytes>, <timeMs>"
```

Resolution rules:
- Expected outcome is derived from the filename: `contains("unmatch")` → `NO_MATCH`; `startsWith("retention_")` → `NO_MATCH`; otherwise `MATCH`. Documented as a comment next to the derivation.
- HA-PG mode iff `--ha-db-params` was provided.
- `LoadTestMain` reads the JSON (classpath first, filesystem fallback — same as `main`), parses the `RuleSet` map once, derives the `RulesSet` and a `rulesetJson` string, and dispatches to `LoadRunner` or `HaLoadRunner` passing the raw `rulesSetMap`. `Payload` construction happens inside the runner's lambda — see §5.2.
- On success, writes the metric line via `MetricReporter` and exits 0.
- On failure, lets the exception propagate — the JVM prints a stack trace to stderr and exits non-zero.

Dropped vs the existing `Main`: the bare `--ha` flag, `--ha-uuid`, `--failover-recovery`, the parallel-execution wrapper (`THREADS_NR`, hardcoded to 1), the `EXECUTE_PAYLOAD_ASYNC` toggle and async-payload reader path, the `EXPECTED_MATCHES` compile-time constant. These come back when migrated scripts need them.

### 5.2 `LoadRunner` (non-HA)

```java
public final class LoadRunner {
    public static Result run(RulesSet rulesSet, Map rulesSetMap,
                             ExpectedOutcome expected, String eventsJson);
}
```

Flow:
1. Create `AstRulesEngine`, `engine.createRuleset(rulesSet)`.
2. `TimedResult t = Measurement.timeWork(() -> { Payload p = Payload.parsePayload(rulesSetMap); return p.execute(engine, id); })` — Payload is constructed and used entirely inside the lambda, so after `timeWork` returns the Payload is unreachable. `Payload.execute` returns an `Execution` wrapper carrying both the match list and `matchCount`; `matchCount` is tracked independently of the Payload's `discard_matched_events` flag so callers can check whether matches occurred even when the list is intentionally empty for memory reasons.
3. `OutcomeCheck.verify(t.matchCount, expected, eventsJson)` — throws on mismatch.
4. `long mem = Measurement.captureUsedMemoryAfterGc()` — the GC dance reclaims the Payload and its event list; no explicit nulling needed.
5. Return `new Result(t.matches, t.durationMs, mem)`.

Why pass `rulesSetMap` instead of a constructed `Payload`: if `LoadTestMain` built the `Payload` and passed it in, LoadTestMain would hold a stack-frame reference to it across the GC dance, inflating the memory reading. Keeping Payload's lifetime inside the runner's lambda eliminates that cross-frame reference. It also avoids the lambda-capture rule that would forbid a later `payload = null` reassignment.

### 5.3 `HaLoadRunner` (HA-PG)

```java
public final class HaLoadRunner {
    public static Result runLoad(RulesSet rulesSet, String rulesetJson,
                                 Map rulesSetMap, String haDbParamsJson,
                                 ExpectedOutcome expected, String eventsJson);
}
```

Flow:
1. Generate a per-run HA UUID: `"loadtest-ha-" + System.currentTimeMillis()`.
2. `engine.initializeHA(uuid, "loadtest-worker", haDbParamsJson, "{\"write_after\":1}")`.
3. `engine.createRuleset(rulesSet, rulesetJson)`.
4. Open a socket to `localhost:engine.port()` (required for HA's `isConnected()` check).
5. `engine.enableLeader()`.
6. `TimedResult t = Measurement.timeWork(() -> { Payload p = Payload.parsePayload(rulesSetMap); return p.execute(engine, id); })` — Payload is scoped to the lambda, same rationale as `LoadRunner`. `t` carries both the match list and `matchCount`.
7. `OutcomeCheck.verify(t.matchCount, expected, eventsJson)` — throws on mismatch.
8. `long mem = Measurement.captureUsedMemoryAfterGc()` — GC dance reclaims the Payload.
9. Return `new Result(t.matches, t.durationMs, mem)`.
10. Close socket in `finally`; socket-close failures `WARN`-log, do not fail the run.

Returns the same `Result` shape as `LoadRunner`.

### 5.4 `Measurement`

Two responsibilities, two methods. The outcome check must run between them, so they are deliberately separated.

```java
public final class Measurement {
    // Time a piece of work and return its result + duration.
    public static TimedResult timeWork(Supplier<Payload.Execution> work);

    // Run the GC dance (System.gc(); sleep(1000); System.gc()) and
    // return the post-GC used-memory snapshot.
    public static long captureUsedMemoryAfterGc();

    public static final class TimedResult {
        public final List<Map> matches;   // empty when discard_matched_events=true
        public final int matchCount;      // always accurate; source of truth for OutcomeCheck
        public final long durationMs;
        // ctor, getters...
    }
}
```

Rationale: the GC dance only produces meaningful numbers if no references to the payload or match list are retained; the caller controls that timing by nulling its local references between the two calls. Centralizing both primitives here keeps the GC discipline out of the runners themselves.

### 5.5 `MetricReporter`

```java
public final class MetricReporter {
    public static void report(PrintStream err, String eventsJson,
                              boolean haPg, long usedMemoryBytes, long timeMs);
}
```

Writes exactly one line to `err`:
```
<eventsJson>[ (HA-PG)], <usedMemoryBytes>, <timeMs>
```

This format is the bash/Java contract: `fmt_parse_metrics` in `common.sh` splits on `,` and expects three fields in this order. Regression-tested by `MetricReporterTest`.

### 5.6 `OutcomeCheck` + `ExpectedOutcome`

```java
public enum ExpectedOutcome { MATCH, NO_MATCH }

public final class OutcomeCheck {
    public static void verify(int matchCount,
                              ExpectedOutcome expected,
                              String eventsJson);
}
```

- `MATCH` and `matchCount == 0` → `throw new RuntimeException("Expected at least one match but got 0 (events: <eventsJson>)")`.
- `NO_MATCH` and `matchCount > 0` → `throw new RuntimeException("Expected no matches but got " + matchCount + " (events: <eventsJson>)")`.

Pure, deterministic, trivially unit-testable.

Why `int matchCount` rather than the match list: `Payload` (copied from `main/`) skips accumulation when `discard_matched_events=true`, which all `24kb_*_events.json` files set to `true` so the 1m-event run doesn't OOM on client-side match retention. A list-based check would therefore see zero matches even when every event matched. `PayloadRunner` maintains `matchCount` as a counter that always increments regardless of the discard flag — the authoritative signal for whether the engine matched anything.

See §7.

### 5.8 `MemoryLeakAnalyzer` (ported and enhanced)

Ported verbatim from `main`, with one enhancement: group by HA mode as well as scenario.

- Existing behavior preserved: parses `<name>, <bytes>, <ms>` lines, sorts groups by size (1k → 10k → 100k → 1M), flags single increases > 50MB (`ABSOLUTE_INCREASE_THRESHOLD`), flags 2+ consecutive 3× accelerations (`INCREASE_GROWTH_THRESHOLD`), flags total increase > 150MB. Exit 0 (clean), 1 (leak/exception), 2 (parse error).
- New grouping: a line with `" (HA-PG)"` after the filename is classified as HA-PG; absence is noHA. Combined with the existing `contains("unmatch")` check, tests are bucketed into four groups — `match/noHA`, `match/HA-PG`, `unmatch/noHA`, `unmatch/HA-PG`. Each group runs independently through the same thresholds. A single suspicious group fails the exit code.

CLI invocation from bash:
```
java -cp target/classes \
     org.drools.ansible.rulebook.integration.loadtests.analyze.MemoryLeakAnalyzer \
     result_all.txt
```

`main`'s copy stays in place, untouched, for now.

## 6. Shell scripts and `lib/common.sh`

### 6.1 `lib/common.sh` — single file, prefixed function names

All scripts start with:
```bash
set -euo pipefail
source "$(dirname "$0")/lib/common.sh"
```

Functions:

| Prefix | Function | Purpose |
|---|---|---|
| `require_` | `require_jar` | Verify fat jar exists; print build command on failure. |
| | `require_docker` | Verify Docker daemon is reachable. |
| | `require_python3` | Verify `python3` (used only for free-port discovery). |
| `pg_` | `pg_setup` | Start `postgres:15-alpine` on a free port, wait for `pg_isready` + `SELECT 1`, export `PG_CONTAINER` and `PG_PARAMS`. |
| | `pg_cleanup` | `docker stop $PG_CONTAINER` — registered via `trap pg_cleanup EXIT`. |
| | `pg_truncate` | Truncate the 4 HA tables (`drools_ansible_session_state`, `drools_ansible_matching_event`, `drools_ansible_action_info`, `drools_ansible_ha_stats`) before each HA run. |
| | `pg_count <table>` | Return row count (or `ERR`). |
| | `pg_blob_size` | Return max length of `partial_matching_events` TEXT column (or `0`/`ERR`). |
| `jvm_` | `jvm_run <label> <args...>` | Invoke `java -Xmx1g -Dorg.slf4j.simpleLogger.logFile=System.out -jar $JAR <args>`, append stdout to `$LOG`, capture stderr into `_run_stderr`. Tolerates non-zero exit (`|| true`) so the caller can record `FAILED` rows. |
| `fmt_` | `fmt_parse_metrics <stderr> <file>` | Extract the last line starting with `<file>`, split on `,`, set `_mem` and `_time` (or `FAILED`/`FAILED` if not found). |
| | `fmt_per_event_kb <bytes> <count>` | Emit `%.1f` KB via awk. |

Script-level shell variables set by helpers (not exported): `JAR`, `PG_CONTAINER`, `PG_PARAMS`, `_run_stderr`, `_mem`, `_time`.

### 6.2 `load_test_match.sh [1k|10k|100k|1m]`

Default size `1k`. Runs `24kb_<size>_events.json` once with noHA, once with HA-PG.

Output `result_match_<size>.txt`:
```
=== Match Load Test (size=<size>) ===
Mode       Events   Memory(bytes)   Time(ms)  Per-Event(KB)
------------------------------------------------------------
noHA       <size>   <bytes>         <ms>      <kb>
HA-PG      <size>   <bytes>         <ms>      <kb>
```

Log file `out_match.log` captures full stdout/stderr per run.

Heap: `-Xmx1g` (unified across all scripts — retention needs it, match/unmatch fits comfortably).

### 6.3 `load_test_unmatch.sh [1k|10k|100k|1m]`

Identical shape to `load_test_match.sh`, but `24kb_<size>_events_unmatch.json`. Outputs `result_unmatch_<size>.txt` + `out_unmatch.log`.

### 6.4 `load_test_retention_noHA_HA-PG.sh`

No args. Keeps the shape of the existing `main/load_test_retention.sh`:
- Uses `retention_100_events.json`, `retention_500_events.json`, `retention_1k_events.json`.
- 6 rows (3 sizes × 2 modes) with columns `Mode · Events · Memory(bytes) · Time(ms) · Per-Event(KB) · MATCHING · BlobSize(B)`.
- Followed by a delta table (per-event incremental cost between sizes for each mode) and an HA-overhead delta table (HA-PG minus noHA per size).
- One PG container for the entire script; `pg_truncate` between HA runs.

Output `result_retention_noHA_HA-PG.txt` + `out_retention_noHA_HA-PG.log`.

### 6.5 `load_test_match_unmatch_noHA.sh` and `load_test_match_unmatch_noHA_HA-PG.sh`

Combined-run scripts split by HA cost profile. A single "run everything" script would either skip HA-PG at large sizes (losing coverage) or force multi-minute runs at 100k/1m HA-PG (too slow for interactive iteration). Splitting the coverage along the cost boundary keeps both halves usable.

- **`load_test_match_unmatch_noHA.sh`** — no args. Outer loop `for size in 1k 10k 100k 1m`; inner loop `for scenario in match unmatch`; mode is `noHA` only. That is 8 runs. No Docker dependency. Emits `result_match_unmatch_noHA.txt` + `out_match_unmatch_noHA.log`.
- **`load_test_match_unmatch_noHA_HA-PG.sh`** — no args. Outer loop `for size in 1k 5k 10k`; inner loops `for scenario in match unmatch; for mode in noHA HA-PG`. That is 12 runs. Sizes cap at 10k because HA-PG becomes prohibitively slow above that; the 5k intermediate point is there so each group has three data points, which `MemoryLeakAnalyzer`'s consecutive-acceleration check requires to fire. One PG container is reused across all HA runs with a `pg_truncate` before each. Emits `result_match_unmatch_noHA_HA-PG.txt` + `out_match_unmatch_noHA_HA-PG.log`.

Each script hands its result file to `MemoryLeakAnalyzer` and exits with the analyzer's exit code so CI (when wired) can gate on it.

## 7. Payload generator and realistic 24KB payload

### 7.1 Generator

`org.drools.ansible.rulebook.integration.loadtests.gen.PayloadGenerator` is a plain `public static void main(String[])`. No args. Writes all 11 JSON files into `src/main/resources/`, overwriting any existing file.

Deterministic: each file contains exactly one event template (duplicated at runtime via `repeat_count`), so every value in the template is a fixed string (no `UUID.randomUUID()`, no `Instant.now()`). The only use of `Random` is inside the seeded filler-text generator — `new Random(42L)` for word shuffling — so repeated runs produce byte-identical output and diffs are meaningful.

Run:
```
mvn -pl drools-ansible-rulebook-integration-load-tests -am install
mvn -pl drools-ansible-rulebook-integration-load-tests exec:java \
    -Dexec.mainClass=org.drools.ansible.rulebook.integration.loadtests.gen.PayloadGenerator \
    -Dexec.classpathScope=compile
```

Not wired into the default build — runs on demand when the template changes.

### 7.2 Event template (~24 000 bytes when serialized)

```json
{
  "event_id": "evt-<uuid>",
  "timestamp": "2026-04-21T10:15:30.123Z",
  "source": {
    "host": "host-<N>",
    "component": "ansible-rulebook",
    "region": "us-east-1",
    "cluster": "cluster-<N>"
  },
  "severity": "INFO",
  "tags": ["eda", "rulebook", "load-test", "synthetic"],
  "labels": { "env": "prod", "team": "platform", "tier": "critical", "batch": "<N>" },
  "metrics": {
    "cpu_pct": 42.7, "mem_mb": 1337, "disk_io_mb": 88.2,
    "net_rx_kb": 1024, "net_tx_kb": 2048, "req_count": 17,
    "latency_ms_p50": 12, "latency_ms_p95": 87, "latency_ms_p99": 201
  },
  "trace": {
    "trace_id": "<hex32>",
    "span_id": "<hex16>",
    "parent_span_id": "<hex16>"
  },
  "message": "<~22KB of readable synthetic log text>",
  "a": 1
}
```

- `message` is the bulk. Filler is built from a ~200-word pseudo-log vocabulary, shuffled and concatenated into sentences like `"connection pool saturated; retrying host-7 after 300ms backoff..."`. The generator appends sentences until the serialized event clears ~24 000 bytes, then truncates at the last whitespace boundary so it stays readable.
- `a: 1` is preserved at the top of the event so the match/unmatch/retention rules can reference `event.a` directly.

### 7.3 Rule-set shapes

| File(s) | Rule | `repeat_count` |
|---|---|---|
| `24kb_<size>_events.json` | one rule, condition `event.a == 1`, action `debug`, `discard_matched_events: true` | 1000 / 5000 / 10000 / 100000 / 1000000 |
| `24kb_<size>_events_unmatch.json` | one rule, condition `event.a == 2`, otherwise same | 1000 / 5000 / 10000 / 100000 / 1000000 |
| `retention_<N>_events.json` | one rule, 2-condition join `event.a == 1 AND event.b == 1` (condition 1 always true, condition 2 never true → partial matches retained) | 100 / 500 / 1000 |

Semantically equivalent to the existing `main` files; `retention_*` replaces the misnamed `failover_*`.

## 8. Error handling

### 8.1 Java
- Uncaught exceptions propagate; JVM exits non-zero; no metric line is emitted.
- `OutcomeCheck.verify` throws before the GC dance, so a semantic failure does not produce a misleading metric.
- `HaLoadRunner` closes the HA socket in `finally`; socket-close failures `WARN`-log, do not fail the run.
- No retry logic. A failing run is visible in the output table as `FAILED`.

### 8.2 Bash
- `set -euo pipefail` at the top of every script.
- `trap pg_cleanup EXIT` in any script that starts PG.
- `require_jar` / `require_docker` / `require_python3` abort early with clear errors.
- `jvm_run` uses `|| true` intentionally: a single-run crash becomes a `FAILED` row rather than terminating the outer loop (critical for `load_test_match_unmatch_noHA.sh` at 8 runs and `load_test_match_unmatch_noHA_HA-PG.sh` at 12 runs).

## 9. Testing

Unit tests only in this module:

- `MeasurementTest` — trivial work lambda; assert non-zero duration and positive `usedMemoryBytes`.
- `MetricReporterTest` — assert exact line format for noHA (`"24kb_1k_events.json, 5200000, 195"`) and HA-PG (`"24kb_1k_events.json (HA-PG), 7100000, 240"`). Regression fence for the bash contract.
- `OutcomeCheckTest` — all four combinations (MATCH/zero, MATCH/non-zero, NO_MATCH/zero, NO_MATCH/non-zero) driven by the `matchCount` int; assert the thrown exception includes the events-json name and, for `NO_MATCH` failures, the actual count.
- `MemoryLeakAnalyzerTest` — fixture result files covering (a) 4 clean groups (no leak), (b) one group with a 200MB single-step spike (leak), (c) one group with two consecutive 3× accelerations (leak). Use a `ParseResult`/`analyzeResults` split so tests avoid `System.exit`.

No JUnit coverage for `LoadRunner` / `HaLoadRunner` — they pull in the full `AstRulesEngine` and DB; the underlying behavior is covered by `main`'s `PerfTest`, `ha-tests`, and the scripts themselves.

No automated script execution in CI — operator-run. CI wiring is a deferred follow-up.
